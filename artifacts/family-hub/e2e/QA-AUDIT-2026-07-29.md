# Family Hub — Full Regression & Consistency Audit (2026-07-29)

Method: 38-screenshot Playwright walkthrough of a brand-new account (real signup,
real Postgres, real session) cross-checked against a full read of the underlying
components, plus a dedicated code-level review of the iCal and Outlook
integrations (which can't be exercised from screenshots). Every finding below was
verified in code at the cited location — nothing is speculative. **No fixes were
made in this pass.**

Totals: **12 high · 20 medium · 25 low** (57 findings).

---

## 1. Landing / Auth

- **[low]** Empty-submit shows the browser's native validation bubble, visually
  inconsistent with the app's styled toasts and rendered differently per
  browser/iOS — fields rely on native `required` with no custom validation UI
  (`landing.tsx`).

## 2. Onboarding wizard

- **[high]** "Which one is you?" → **Continue is a hard dead-end** when the user
  changes nothing (the most common case — email/photo are optional): red
  "Couldn't save profile" toast, step never advances; only Skip escapes — the
  mutation sends `{ email: undefined, photoUrl: undefined }`, JSON serialization
  strips both, the empty `{}` PATCH throws drizzle's "No values to set"
  (`onboarding-wizard.tsx:189-195` → `routes.ts:210` → `storage.ts:567`).
  Side-effect: the login never gets linked to the profile, so Settings later
  shows it under "Logins not linked to a person above."
- **[low]** `completeOnboardingMutation`'s comment claims "retry silently once"
  but no retry is configured, and `markStep` invalidates onboarding-status
  without awaiting the PATCH (stale-refetch race) — comment/code drift
  (`onboarding-wizard.tsx:587-590, 614-622`).
- **[low]** Quick Tour tells users to find "Settings → Tab Order & Visibility,"
  but the section is titled "Display & Layout" — copy not updated after the
  section rename (`onboarding-tour.tsx:261`).

## 3. Home tab

- **[medium]** Events card subtitle reads "**0 family members •0 events**" on a
  fresh account (and "0 family members • 5 events" after deselect-all) — it
  prints raw `selectedProfiles.length` instead of the effective everyone-filter,
  and a JSX newline collapses the space after "•" (`home-view.tsx:1067-1070`).
- **[medium]** Achievements and Tasks (progress) cards show misleading empties
  ("No achievements yet!", "Nothing remaining today") after deselect-all — both
  filter strictly on `selectedProfiles` instead of the app-wide "empty selection
  = show everyone" convention the Events/Activity/Stars cards in the same file
  follow (`home-view.tsx:870-871, 937, 1409-1414`).
- **[medium]** Home's Today's Events omits **Outlook and iCal events entirely**
  (People tab omits iCal) — only Google queries exist in these views, so an
  Outlook/feed-only family sees an empty Home card while Calendar shows the
  events (`home-view.tsx` has zero outlook/ical references;
  `people-view.tsx:1331-1436`).
- **[medium]** Checking off an inspiration/note has no `onError` — a failed
  toggle silently reverts on next refetch (`home-view.tsx:783-798`, the only
  mutation in the file without an error path).
- **[low]** Dead work every render: `recentChoreAchievements` computed and never
  read; orphan `HealthTodayCard` still imported (`home-view.tsx:31, 885-909`).
- **[low]** Driver-name pill can hard-clip long names and squeeze the title to
  zero width — `flex-shrink-0` pill + clip-only overflow
  (`home-view.tsx:1119-1142`).

## 4. Calendar tab

- **[high]** Only Google gets a sync-error banner; **Outlook and iCal fetch
  errors render as zero events with no signal** — `googleSyncError` has no
  Outlook/iCal equivalent and both queries' `isError` is never read
  (`calendar3-view.tsx:677, 679-696, 1338`; same in `people-view.tsx`). Combined
  with the Outlook token bug (§12) an expired connection is indistinguishable
  from an empty calendar.
- **[low]** Event mutations mix generic vs. server-message error toasts —
  delete-Google surfaces `error.message` but create/update/delete-local don't,
  losing the backend's specific 403/timezone hints (`home-view.tsx:385-457`,
  `calendar3-view.tsx:930-984`).
- **[low]** React "unique key prop" console warning fires in `FamilyHub` on
  first Calendar open — an unkeyed list in the render path (observed in the
  live run).

## 5. Chores tab (Tasks, Rewards, Bonus, Trophies)

- **[high]** **Editing a task through the unified Manage drawer silently
  rewrites fields the form doesn't show**: `buildBody` hardcodes `points: 0`
  for to-dos (zeroing stars a to-do legitimately carried), resets
  `daysOfWeek`/`recurrenceType` for to-dos/inspiration, and forces `weekly` on
  regular chores — the create-payload builder is reused verbatim for edit
  PATCHes with no per-field diffing (`create-task-modal.tsx:203-215, 251-259`).
- **[high]** Bulk Add Chores: a mid-loop failure leaves a silent partial batch
  (no try/catch, no error toast; retry duplicates the successes) — sequential
  awaits with feedback only after the full loop (`chores-view.tsx:2641-2650`).
- **[high]** PIN verification discards the server's message, so the deliberate
  rate-limit lockout response ("too many tries") never reaches the user — they
  see generic "Couldn't verify PIN" and keep retrying
  (`rewards-view.tsx:546`).
- **[medium]** "No family members selected" renders under the Chores card even
  when All Family is active with a profile present (screenshots 17/38) — the
  per-profile list treats empty selection as an error state instead of
  everyone (`chores-view.tsx:1156-1157`; same string in
  `trophy-case-view.tsx:652`).
- **[medium]** The unified Manage drawer is gated `"createChore"` from the
  Chores card but `"createBonusChore"` from the Bonus card — a family that
  PIN-gates chores but not bonus lets a kid open the full task list from the
  Bonus card (deletes stay kind-gated; exposure/labeling inconsistent)
  (`family-hub.tsx:1089, 1202, 1532`).
- **[medium]** Drag-reorder in the Manage drawer uses HTML5 `draggable`, which
  never fires on iOS/WKWebView — dead on the primary platform; todos-view
  documents and uses the pointer-events pattern for exactly this reason
  (`chore-management-drawer.tsx:219-224`).
- **[medium]** Dead trigger counters (`choresAddTrigger`,
  `choresManageTrigger`, `choresManageOpenTrigger`, `bonusAddTrigger`,
  `bonusManageTrigger`, `addEventTrigger`) are only ever reset — no incrementer
  exists anywhere — yet still threaded into three views' `useTriggerEffect`
  machinery (`family-hub.tsx:355-357, 373-374, 413`).
- **[medium]** Bonus Chores retains an unreachable legacy Add/Edit dialog +
  Manage sheet whose edit form (if ever reached) drops icon and claim-scope —
  legacy per-card management left mounted after the unified drawer took over
  (`bonus-chores-view.tsx:561-733`).
- **[medium]** Bonus list has no loading gate — "No bonus chores yet…" flashes
  every cold load, the exact pattern already fixed with spinners in
  chores/rewards/Home (`bonus-chores-view.tsx:286-288, 453-460`).
- **[medium]** Star Insights family view: "Perfect days — days everyone
  finished" actually shows the **sum of per-person** perfect_day rows (two kids
  perfect the same day = 2) — per-person metric relabeled without recomputation
  (`stats-insights-card.tsx:221, 268`).
- **[low]** "pts" suffix survives the Stars-everywhere wording decision
  (`chores-view.tsx:1312`, `trophy-case-view.tsx:860`).
- **[low]** Trophy standalone header sums completion points client-side instead
  of the authoritative `/api/points` balance (mitigated: only the embedded
  variant renders in-app) (`trophy-case-view.tsx:537-546, 741`).
- **[low]** Manage drawer ignores its `noun` prop in the footer/tooltips — the
  "Manage To-Dos" drawer reads "N chores total"
  (`chore-management-drawer.tsx:325, 335, 366`).
- **[low]** ⭐ points pill renders on to-do/inspiration rows in the drawer —
  kinds defined as never earning stars show "⭐ 0"
  (`chore-management-drawer.tsx:313-316`).
- **[low]** Permanently-dead Spin-the-Wheel modal still mounted behind a
  hardcoded-false flag (`chores-view.tsx:241-243, 2654-2659`).
- **[low]** One dialog mixes nouns/casing: title "Create New Task", submit

- **[low]** Add/Edit "Assign to" is Radix Select while sibling

## 11. Backend issues surfaced by the walkthrough

- **[high]** `/api/weather` is **unauthenticated and cross-tenant**: it reads
  `getLocationSettings()` = `SELECT … LIMIT 1` over the whole table, serving
  whichever family's location sorts first — missing userId scoping
  (`routes.ts:3887-3893`, `storage.ts:967-970`).
- **[high]** Weather failures return **status 500 carrying a "graceful"
  fallback body that the client can never use** — the default queryFn rejects
  all non-2xx, so the intended degradation is dead code and the widget blanks
  (`routes.ts:3949-3960` + `weather-widget.tsx:33-35`).

## 12. iCal & Outlook integration (dedicated code review)

### High

- **[high]** The **entire Outlook read path never refreshes an expired access
  token** — Graph tokens live ~1h; after that, events, available-calendars,
  and write-target validation all 401→500 until a two-way-sync *write* happens
  to refresh the row or the user reconnects; only `calendarSync.ts` refreshes
  (`routes.ts:3740, 3787, 3866` vs. Google's auto-refresh at
  `googleCalendar.ts:126-129`).
- **[high]** **Recurring Outlook events are never expanded** — the code calls
  `/me/calendars/{id}/events` (series masters only) instead of
  `/calendarView`; a weekly meeting shows once on its original date, and a
  series whose master starts >1yr ago is `$filter`ed out entirely — silent
  data loss vs. Google's `singleEvents: true`
  (`outlookCalendar.ts:92-101`).
- **[high]** **All-day iCal events land on the wrong day** for anyone west of
  the server's timezone — date-only DTSTART is serialized via
  `toJSDate().toISOString()` (midnight UTC) and parsed raw client-side, so a
  Jul 15 event renders Jul 14 evening in the US; verified empirically against
  the repo's own ical.js. The fix pattern already exists in
  `calendarImport.ts` (noon-UTC anchoring) and was never applied here
  (`icalCalendar.ts:131-141` + `calendar3-view.tsx:848`).
- **[high]** Outlook/iCal fetch failures are invisible in every view (see §4)
  — the "broken feed looks like no events" failure mode.

### Medium

- **[medium]** Pressing **Reconnect wipes `selectedCalendarIds` and
  `writeCalendarId`** — the OAuth callbacks call save-tokens
  (deactivate+insert) without carrying the old row's selection forward; the
  historical silent-refresh bug was fixed in `calendarSync.ts:72-73` but not
  here, and the Google callback has the identical gap
  (`routes.ts:3697-3704, 2782-2791`).
- **[medium]** No timeout on any Outlook Graph call (axios default = infinite),
  and calendars are fetched sequentially — one hanging endpoint blocks the
  events request indefinitely; the iCal path has a 15s abort
  (`outlookCalendar.ts`, whole file, vs. `icalCalendar.ts:65`).
- **[medium]** `$top: 500` with **no pagination** — calendars with >500 events
  in the ±1yr window silently drop the rest; Google's `nextPageToken` loop was
  the explicit fix for this same issue (`outlookCalendar.ts:99`).
- **[medium]** Per-calendar Outlook failure is a `console.warn` and partial
  results return as success — one broken calendar quietly disappears with no
  partial-flag and no frontend error surface (`outlookCalendar.ts:117-120`).
- **[medium]** Outlook refresh failure on the write path falls back to a stale
  token and records `syncState: "error"`/`lastError` — **which no frontend
  code reads anywhere** — so two-way sync can stop permanently (e.g. revoked
  consent) with no user-visible signal ever (`calendarSync.ts:76-80`; zero
  `syncState` matches in `family-hub/src`).
- **[medium]** iCal subscription fetch has **no SSRF protection** — plain
  `fetch` of a user URL with redirects followed; the repo's other ICS fetcher
  (`calendarImport.ts`) is explicitly SSRF-safe, so the requirement was known
  (`icalCalendar.ts:57-69`).
- **[medium]** Feeds with TZID but no VTIMEZONE (some school/sports systems)
  resolve as floating times in the **server's** timezone — a 5-6h shift on
  timed events, silently; verified empirically (`icalCalendar.ts` parse path).
- **[medium]** Home/People provider coverage gaps (§3) are part of this
  integration's inconsistency footprint.

### Low

- **[low]** Malformed VEVENTs are skipped via `catch { continue }` — a feed
  whose events *all* fail parses "successfully" as 0 events with
  `lastError: null` (`icalCalendar.ts:104-165`).
- **[low]** iCal feeds fetched sequentially: N broken feeds ≈ N×15s worst case
  per cache-miss request (`routes.ts:3052-3071`).
- **[low]** No server-side caching/rate limiting for Outlook (or Google) event
  reads — N+1 Graph calls per profile per view past the 60s staleTime;
  theoretical at family scale.
- **[low]** Outlook redirect URI is built from `REPLIT_DEV_DOMAIN` with no
  visible scheme prefix — works in the deployed env, unverifiable statically
  (`routes.ts:3643`).

### Verified solid (checked and cleared)

iCal fetch hardening (15s timeout, `res.ok` check, VCALENDAR sniff rejecting
HTML login pages, webcal:// normalization, per-feed `lastError` surfaced in
Settings); iCal RRULE expansion incl. RECURRENCE-ID exceptions and a 750-occ
cap; the historical Outlook silent-refresh bug fixed at `calendarSync.ts:72-73`;
selectedCalendarIds/writeCalendarId honored and validated on their main paths;
all-day exclusive-end fix applied at every calendar3-view/people-view mapping
site; two-way-sync dedup on both providers; `lib/confirmDialog` and
`lib/parentGate` clean; no `window.confirm` anywhere; Stars terminology
consistent except the two "pts" stragglers; flyer-sheet overflow handling now
exemplary.

### Not verifiable statically

Live Graph `$filter` semantics with Z-suffixed timestamps; whether
`REPLIT_DEV_DOMAIN` includes a scheme; proxy-level request timeouts that might
mask the missing axios timeout; Microsoft's `expires_in` always being present.
